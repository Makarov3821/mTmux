# 下一阶段评估：语音输入、界面语言与云同步

日期：2026-09-25。基线：0.6.5-dev。本文件仅为评估/计划，不代表功能已经交付；本轮不改应用代码、不升级 APK。

## 1. 是否只剩语音

按近期用户选择的优先队列，独立语音入口确实是主要剩余功能；原始完整计划尚未清空。仍暂缓：设备生成 SSH 密钥、手动 tmux 目标、自定义 socket / SSH config 导入、手机与电脑独立显示焦点/尺寸、逐行/五行滚动模式、系统性弱网性能验证和发布准备。发布签名、真实设备覆盖、一周日常试用也不等于已验收。

本轮将“中英文界面”和“云同步”加入优先队列，覆盖旧文档中“跨设备同步暂缓”的优先级，但不同时重启其他暂缓功能。

建议顺序：**中英文资源化 → 系统语音入口 → 可移植加密备份 → GitHub 同步**。把备份作为同步的基础，可先交付可验证的恢复能力，避免先做上传按钮、后补数据安全与合并。

以下工期为一名熟悉本仓库的 Android 工程师的粗略人日估算，含常规自动化/设备验证，不含等待服务申请、商店审核和独立安全审查；不是交付承诺。延迟/体积若无官方数字则是规划目标，不是本 App 实测。

## 2. 语音输入方案比较

> 2026-10-02 更新：用户明确希望保留带语音/不带语音两个版本，并优先完全离线的轻量多语种模型。新的主计划见 [双版本语音输入实施计划](voice-input-plan.md)：先基准 whisper.cpp multilingual tiny/base q5_1，再以 standard/voice flavors 交付；本节早期“系统 SpeechRecognizer 首选”的结论仅作为历史评估，由新计划覆盖。

| 方案 | 包体/磁盘、内存与 CPU | 延迟/质量特点 | 网络与运营成本 | 估算工作量与建议 |
| --- | --- | --- | --- | --- |
| 保留输入法语音 | App 几乎无新增资源；资源由输入法承担 | 取决于输入法；用户已经能用，但入口不统一 | 服务方决定是否联网；App 无自营识别账单 | 0.5–1 人日补使用说明/验证，作为永久回退 |
| 系统识别弹窗 `RecognizerIntent` | App 无模型，增量很小 | 接入快，界面和支持情况依赖系统；外部 Activity 可能触发当前 onStop 断连逻辑 | 可能在线，无自营模型服务 | 1–3 人日；不作为首选，避免破坏终端流程 |
| **应用内调用 `SpeechRecognizer`** | App 不捆绑模型；本地模型由系统服务管理。App 侧开销小，不代表整机离线识别零耗电 | 可做自己的录音面板、部分结果和停止按钮；服务/机型差异需要测试 | 设备识别可离线，普通识别可能传音频到服务商 | **4–7 人日，首选**；不保证所有 Android 都有可用服务 |
| 自带 Vosk / sherpa-onnx 等离线引擎 | 模型和 native runtime 增加磁盘、内存。Vosk 官方典型小模型约 50 MB、运行约 300 MB；sherpa-onnx 是框架，成本必须按所选模型测量 | 可流式，不依赖系统服务；技术术语、中英混说质量须实测，不能按框架名保证 | 下载后不需识别网络；有模型分发/升级成本 | 8–15 人日；适合无系统服务用户，后续可选下载 |
| whisper.cpp 多语言离线模型 | 官方参考：tiny 75 MiB / ~273 MB RAM；base 142 MiB / ~388 MB；small 466 MiB / ~852 MB。这些不是本机 Android 峰值测量；量化可降低成本 | 手机 CPU/散热差异大；能做边录边分块，但流式体验需自己处理，并非直接获得成熟流式服务 | 下载后可离线；高于系统接口方案的功耗和维护负担 | 10–20 人日；不默认塞入轻量安装包；中文不能选 `.en` 模型 |
| 第三方云 ASR API | 手机主要录音/编码/网络，模型不占手机磁盘；App 是否需 SDK 取决于供应商 | 通常提供流式结果，但质量/延迟取决于语言模型、网络和端点；技术词并非必然正确 | 按音频时长计费；需用户自带凭据或我们维护鉴权/计费后端 | BYO 单供应商约 5–9 人日；自营服务约 10–20 人日以上并有持续运维 |
| 自有服务器 ASR | 手机轻，服务器承担模型 RAM/CPU/GPU；仍需录音上传 | 可控模型/词汇，公网延迟、并发排队和服务器负载决定体验 | 有已有服务器可复用，但不是零算力/维护成本 | 8–15 人日，另计服务部署；仅为用户自选，不在 SSH 主机静默安装 |

系统服务的设备端入口从 API 31 提供，需先检查可用性；本项目最低 API 26 必须保留普通识别/键盘路径。普通服务可能联网，不能把“优先离线”选项当作确定离线保证；无设备端服务时不得在用户选择“仅离线”后静默切到云。按可用 API 检查指定语言/模型支持，不把服务存在等同中文可用。[Android SpeechRecognizer](https://developer.android.com/reference/android/speech/SpeechRecognizer)、[RecognizerIntent](https://developer.android.com/reference/android/speech/RecognizerIntent)

离线模型资源参考：[Vosk 模型列表](https://alphacephei.com/vosk/models)、[whisper.cpp 资源表](https://github.com/ggml-org/whisper.cpp#memory-usage)。不能把其他平台的 RAM 或准确率结果直接当成本应用手机基准。

成本例子：Google Cloud Speech-to-Text V2 Standard 第一档标价为 $0.016/分钟；按每天 10 分钟、每月 30 天计算约 **$4.80/用户/月**，100 个同等用量用户约 $480/月，仅为该档识别费示例，不含其他费用，不套用批处理价格到交互语音。实际还要核对所用模型/地区和合约；价格查阅日期为本文件日期。[官方价格](https://cloud.google.com/speech-to-text/pricing)

网络量例子（计算值）：16 kHz、单声道、16-bit PCM 每分钟约 1.83 MiB；如果服务支持 24–32 kbit/s 音频编码，音频载荷约 0.17–0.23 MiB/分钟，另加协议开销。不能假设系统识别服务采用哪个编码。

### 推荐交互与边界

- 底部“工具”中先放“语音输入”，点击打开紧凑底部面板；暂不把已有底栏再挤成五等份。面板有识别语言（中文/English）、开始/停止/取消、当前结果、加入草稿。识别语言独立于界面语言，首版不承诺自动中英混合检测。
- 优先设备端识别；不可用时明确展示系统服务路径及其可能联网的含义。系统服务也不可用则回到键盘/输入法语音，不能死循环重试或要求安装我们自营服务。
- 只在前台、主动点按后申请麦克风权限并录音；单次上限先定 60 秒，不做常驻/连续监听。离开页面、锁屏、切后台或取消时释放录音与 recognizer。
- 中间结果只展示，最终结果先确认再加入草稿，保留追加/替换/取消；录音不能直接发送命令。沿用连接代次与 pane 保护，断线/切换后迟到的识别回调不得填入其他任务，更不能发出旧输入。
- 音频默认不落盘，转写文字不进调试日志或云同步；若特定识别实现需要临时文件，限定本机私有缓存并在完成/取消/失败后删除，启动时清扫残留。
- 语音面板不重建终端、不触发 PTY 尺寸来回变化，复测键盘锚点和终端阅读位置。

### 实测计划与通过条件

选择用户 Android 15 手机、至少一台较低性能机和一台无 Google 服务/识别服务不同的机型。每条路径使用同一组 30–60 条中文、英文、中英技术词语料（含 SSH、tmux、文件路径、参数和噪声），测中文 CER / 英文 WER、专有词正确率、人工改字量、首段/最终延迟 P50/P95、App 与识别进程的总内存、CPU、温升/耗电、上传量。

首版体验目标：准备好模型且网络正常时，点击后 1 秒内出现录音反馈，停止后最终结果 P95 争取不超过 3 秒；这是验收目标，尚未测得。10/30/60 秒长短句分别测试。拒绝权限、无语言模型、断网、来电/麦克风占用、静音、取消、后台切换、迟到回调均须可恢复；任何失败均不能清空已有草稿或发送远端输入。

## 3. 设置中的中文 / English / 跟随系统

> 已在 0.7.0-dev 实现，见 [0.7.0 记录](../releases/0.7.0.md)。与本节计划的差异：默认资源为英文（非中文系统显示英文）；Android 12 及以下持久化、TalkBack 与真机尚未验证。

建议增加“语言 → 跟随系统 / 简体中文 / English”，初始跟随系统；不改变服务器别名、用户快捷回复、终端原文、命令或 Agent 输出。语音识别语言单独设置。

当前界面和核心错误文本大量直接写在 Kotlin 中；工作主体是资源化和边界回归，不是新增一个选择框。预计 **3–5 人日**，App 体积仅增加文本资源，不引入翻译模型或翻译网络服务，CPU 开销可忽略。

实施：

1. 新建中文/英文 string resources，使用占位符/plurals，覆盖主页、文件夹、认证/跳板、弹窗、终端工具、快捷键无障碍说明、系统保存结果与错误提示；不拼接已翻译句子。
2. 核心连接错误/进度改为稳定错误码/阶段＋参数，在 UI 层本地化。当前 `DebugLog.stage` 根据中文词识别阶段，应一并改成结构化阶段，不能切英文后日志阶段全部变未知。诊断事件名与机器字段维持稳定，不跟着界面翻译。
3. Android 13+ 对接系统应用语言设置；较低版本采用 AndroidX 兼容方案。当前 Activity 是 `ComponentActivity`，不能直接假设加入一行 AppCompat API 就完成兼容；需核对 Activity/locale context 的接入方式和 manifest/localeConfig。[Android 官方应用语言指南](https://developer.android.com/guide/topics/resources/app-languages)
4. 语言变更可能重建 Activity；当前 `onStop/onDestroy` 会断开 SSH。首版设置入口在首页，按当前已有离开终端流程切换；不承诺在活跃终端内无断线切语言，也不为了此功能直接改变后台断线策略。测试草稿/配置不会意外丢失，重建不触发多余探测；若未来要求任意时刻无断线切换，应单独移出连接生命周期管理。
5. 验证英文字长对窄屏底栏、认证按钮、F 键页、文件夹和弹窗的影响；三种主题、Android 26/32/33+/15、系统内切换、重启持久化、缺失资源回退和 TalkBack 均覆盖。

## 4. 云同步：GitHub 是否合适

本计划先假设目标是跨设备恢复和同步**服务器配置及凭据**，而不是远程传输终端画面。符合此前“一次保存后直接连接”的产品方向：开启同步时明确包含密码、私钥及口令，统一以端到端加密的配置库保存；提供“只同步配置、不含凭据”作为可选项，不强迫每台设备重新录入所有私钥。

| 后端 | 对用户的利弊 | 客户端/运营开销 | 并发与历史 | 结论 |
| --- | --- | --- | --- | --- |
| **GitHub 私有仓库** | 开发者已有账号；可查看版本，但 token 配置有门槛，访问质量依网络地区而异 | 仅 HTTPS API，不带 Git 引擎、不 clone 仓库；无我们自建同步服务器 | 更新需旧文件 SHA，可检测并发；每次上传产生 commit；密文历史会累积，不能提供明文 diff | **按当前用户群先做**，低频配置同步适配较好 |
| **WebDAV / Nextcloud / NAS** | 不依赖 GitHub，适合已有网盘/NAS 用户；不同服务器认证/证书兼容有成本 | HTTPS GET/PUT，客户端轻，复用现有存储 | 用 ETag/条件写防覆盖，版本历史取决于服务器；必须测目标服务实现 | 推荐第二后端；已有可靠 WebDAV 时也可优先于 GitHub |
| **已有 SSH 主机上的 SFTP** | 用户已有服务器，可复用网络/SSH 信任和认证；没有云账号要求，但同步主机本身的登录参数须先手动建立 | 可以复用 SSH 栈；无需常驻服务，有连接握手成本 | 原子改名不等于条件更新；跨客户端锁/并发需另外设计 | 很适合加密备份；不以“上传文件成功”冒充完整双向同步 |
| S3 兼容对象存储 | 小配置存储量少，但 bucket/凭据设置偏技术，收费取决于服务 | 签名/权限/地区/厂商兼容中等工作量；请求/存储费用归账号 | AWS S3 支持条件写；兼容服务必须逐一确认，版本控制另计存储 | 后续专业选项，不是首版最省事路线 |
| Google Drive appDataFolder | 面向 Google 用户体验较自然，应用专属目录与授权范围；国内网络/无 Google 服务场景受限 | OAuth 集成与项目配置，客户端开销较小；无需我们存数据 | 应用仍要处理冲突，隐藏目录不适合用户手工查看 | 若用户群偏 Google 生态再加；不是通用首选 |
| 自建账号＋同步服务 / 托管数据库 | 登录简单、设备管理空间大 | 需要认证、权限、数据库、备份、监控、迁移与长期运维；跨平台最灵活 | 可做实时同步，复杂性最高 | 目前配置数据很少，投入不划算 |
| Android 系统备份 / 单独 iCloud | 对换机或各自平台便利 | 受平台机制约束；当前 Android 禁用系统备份且凭据有设备密钥绑定 | 不等于可控的跨 Android/iOS 双向同步 | 不作为此次统一同步方案 |

GitHub 官方文件 API 提供读取/更新、旧 SHA 和 Contents 权限；用选定仓库的 fine-grained token，不要求用户开放全部仓库。[GitHub Contents API](https://docs.github.com/en/rest/repos/contents)

WebDAV 条件操作以 HTTP/WebDAV 规范为基线，不能假设任意网盘都正确实现 CAS；接入前必须用并发测试验证，不支持条件写的服务只提供明确的备份/恢复模式。[WebDAV RFC 4918](https://datatracker.ietf.org/doc/html/rfc4918)

其他后端依据：[S3 条件写](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)、[Drive 应用数据目录与专用 scope](https://developers.google.com/workspace/drive/api/guides/appdata)。以上对运维/开发开销的判断是本项目工程评估，不是服务商性能保证。

### 同步什么

| 数据 | 首版处理 |
| --- | --- |
| 服务器、别名、端口、用户名、tmux 路径、跳板链、认证凭据 | 加密同步；导入后重新用目标设备 Keystore 加密本地保存 |
| 文件夹归属、顺序、快捷回复模板 | 加密同步；记录稳定 UUID 与删除标记 |
| 主题、字号、触控速度、界面语言、文件夹展开状态 | 默认本机保留，跨手机尺寸/使用习惯可能不同；以后可选同步偏好 |
| 主机密钥信任记录 | 可放入加密备份作历史参照；新设备展示待确认指纹，不因拉取配置而静默扩大信任；首次核对后仍可一键连接 |
| tmux 缓存、任务状态灯、最近 pane 身份、草稿、终端内容、语音音频、调试日志 | 不同步；远端列表由该设备刷新，避免过期身份/隐私和流量问题 |
| GitHub token / WebDAV 密码 / 同步恢复密钥 | 本机安全保存，不放回同一个同步库；新设备必须先获得后端访问与解密能力 |

### 跨设备加密与恢复

现有 Android Keystore 密文不能直接复制到另一台设备解密。需要独立的可移植加密格式，不能上传现有 SharedPreferences 文件当同步。

- 首次开启生成随机配置库密钥，使用成熟 AEAD 实现（例如 AES-256-GCM），每次加密使用新 nonce；schema/version/vault identity 等元信息认证保护。禁止自行设计密码算法。
- 用同步口令或恢复密钥解锁配置库密钥；口令采用经过审查的 KDF（优先评估 Argon2id，实现依赖/平台兼容和低端机参数需实测）。代价主要发生在解锁，不每次上传重复跑昂贵 KDF。在本机用 Keystore 包装缓存密钥。
- 新设备只需后端授权＋同步口令/恢复密钥，再把解密的 SSH 凭据按本机方式加密保存。口令与恢复密钥都丢失时无法由 GitHub 或我们代解密，应在设置时明确恢复流程。
- 整个配置库均加密，仓库仅放密文与必要版本头，不以私有仓库权限替代加密。token、同步口令和解密文本不写 debug 日志。
- Git 历史会保留旧密文；更换当前密码不能让旧版本消失。恢复旧版本须有明确提示，不能把“能检测当前设备已见过的旧版本”说成“能防止所有新设备上的回滚”。未来需迁移库/轮换密钥时提供独立流程。

### GitHub MVP 的交互、冲突和流量

1. 设置“云同步 → GitHub”：填写专用私有仓库、分支与路径，配置仅该仓库的 Contents 读写 token；检查可访问/可写/私有状态。首版不自动建库、不自动创建分支、不强制修改受保护分支。后续再评估授权登录，不能在客户端捆绑 GitHub App 私钥或开发者服务密钥。
2. 首次连接如远端为空，展示将上传的数据范围；非空则先验证/解密并展示导入或合并预览，不能用空本地覆盖远端。仓库不再私有、token 失效、分支策略拒绝时停止同步并给出本地可继续使用的提示。
3. 后端接口分为 read(version+payload) 和 compare-and-swap write(expectedVersion,payload)。GitHub 用文件 SHA，WebDAV/S3 用经验证的条件写。GitHub 同一文件写入串行，冲突重新读取后合并，不能用强制覆盖消掉 409。
4. 本地保存 base/local/remote 三份逻辑状态，以 UUID 做三方合并；不同条目修改可自动合并，同一条目的冲突（尤其密码/密钥、跳板、删除对修改）提示用户选择。本地时间戳仅供展示，不作为覆盖胜负依据。保留删除 tombstone；首版不做自动清理，避免长期离线设备把已删配置复活。
5. MVP 首先提供“同步现在”“预览变更”“上次成功/失败状态”。可选自动同步只在首页外部进入且距上次检查≥30分钟、或本地配置变更后防抖触发；不与服务器 tmux 嗅探耦合，不每次刷新状态灯就写 commit，不常驻后台轮询。语音输入/终端输出不触发同步。
6. 网络失败/限流按退避与服务端提示重试；断点失败、进程结束不得删本地配置。仅成功验证远端写入后推进 base；损坏/新 schema 版本库保留本地，拒绝不可理解的覆盖。
7. 以 100 台服务器、每个私钥约几 KiB 做基准，普通库应远小于日志大小；这只是基准假设，大密钥/多级跳板会增加体积。1 MiB 以下典型 GitHub Contents 返回 Base64，载荷约增 1/3；超过 1 MB 的读取需使用其 raw 模式等官方支持路径，不能无限沿用 content 字段。计划将首版解密后库上限定为 8 MiB，超限明确拒绝，解密/解析/解压（如后续采用压缩）都设上限，不静默截断数据。
8. 20 次/日、每次上传下载合计约 100 KiB 的示例约 2 MiB/日，**仅是指定数据量下的计算，不是实测用量**。优化优先减少无变化请求和无内容变化的重新加密上传；Github 历史中的密文不可读 diff，不承诺 Git 有效压缩随机密文。

验收：双设备同时改不同/相同配置、删除与编辑冲突、离线后重连、首次空端、网络中断、token 过期/撤销、受保护分支、远端损坏、旧 schema、错误口令/篡改密文、密钥恢复、导入后目标设备登录、日志敏感内容排除、主机指纹变化拦截。云端变化不得向当前 SSH 会话发送任何输入，也不得自动重连服务器。

## 5. 建议实施拆分与投入

| 步骤 | 可评审交付 | 估算 |
| --- | --- | --- |
| A：双语 | 中/英/系统选择、资源化、稳定错误/日志阶段、窄屏验证 | 3–5 人日 |
| B：语音 | 能力检测、应用内录音面板、设备端优先/明确回退、草稿确认、权限与取消测试 | 4–7 人日 |
| C1：配置库基础 | 版本化 schema、可移植加密、加密文件导入导出、恢复和 Keystore 迁移 | 4–6 人日 |
| C2：GitHub 传输 | 最小权限配置、仓库检查、条件读写、错误/限流、手动同步入口 | 3–5 人日 |
| C3：多端同步语义 | 三方合并、冲突界面、删除标记、防抖、双设备/中断验证 | 4–7 人日 |
| 后续：WebDAV | 复用配置库/合并逻辑，新增认证、ETag 条件写与服务兼容测试 | 3–5 人日增量 |

推荐前三大方向总量约 **18–30 人日**（A+B+C1+C2+C3），后端/模型服务授权等待不计。同步明显比语言切换和语音按钮复杂，不宜并入一个“顺手加上”的小版本。第一版不同时引入离线模型包、自营 ASR、实时后台同步或多个云后端。

计划中的默认决策：先做系统语音服务；界面中文/英文/跟随系统；GitHub 为第一同步后端、WebDAV 为优先替代；凭据支持端到端加密同步，设备显示偏好留本地。进入实现前可根据真机识别服务可用性与用户实际存储条件调整，而不是现在提前安装服务或申请账号。
